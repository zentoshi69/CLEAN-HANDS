# CLEAN Hands App Audit — Harsh Review and Path to 9/10

**Audit date:** 22 June 2026  
**Primary scope:** `staking-api/webapp/` and the supporting staking API  
**Target product:** the production soft-staking Telegram Mini App, not the separate points demo in `miniapp/`

## Executive verdict

**Harsh score: 5.0/10.**

This is a polished prototype with a memorable visual identity and unusually thoughtful wallet-flow test coverage. It is not yet a 9/10 financial product. The gap is not “more polish.” The gap is trust, money-path integrity, accessibility, production proof, and operational transparency.

The repository's existing **9.2/10 self-audit is not supportable**. It misses multiple material issues, including a referral-boost gaming path, fail-open balance verification during claims, unsafe multi-worker accrual, mutable payout destinations, a broken public route, known dependency vulnerabilities, and major WCAG failures.

**Release recommendation:** do not publicly repeat the 9.2/10 claim and do not scale to multiple workers until the P0/P1 findings below are closed and independently retested.

## What is genuinely strong

- The visual language is distinctive and consistent. The glove, pale-blue palette, Fraunces display type, restrained glass treatment, and micro-motion feel authored rather than templated.
- The production Mini App and API share one source of truth.
- Wallet ownership uses an ed25519 signature and a single-use nonce.
- Burn verification checks mint, authority, and finalized Solana transactions.
- Integer base-unit accounting, append-only ledger records, reconciliation tooling, reduced-motion support, and the wallet round-trip tests are solid foundations.
- The 390 × 844 browser review showed good small-screen composition on onboarding, dashboard, trade, boost, and wallet-picker surfaces.

These strengths explain why the app can feel like an 8/10 in a screenshot. The hidden system behavior is what pulls the product to 5/10.

## Critical findings

### CH-01 — The product promise hides the actual lock and payout model

**Severity: P0 — trust and conversion**

The welcome screen says “Earn without locking — tokens stay in your wallet.” Tokens are not locked, but rewards are locked for 90 continuous days, all pending rewards are forfeited on unstake, a $5 fee is deducted from claims, and claims only create a manual payout request.

The interface discloses the lock after login through `lockNote`. That is too late. A reasonable user can connect and stake without understanding the real exit economics. The claim success UI then says **“Claimed”** even though the backend returns `status: "requested"` and no token transfer has happened.

**Evidence**

- `webapp/index.html`: onboarding copy and soft-stake copy.
- `app.py`: default `STAKE_CLAIM_LOCK_DAYS=90`, unstake forfeit, claim fee, and manual claim creation.
- `webapp/app.js`: post-login disclosure and “Claimed” toast that ignores the requested state.

**Required change**

- Replace the headline with precise language: **“Non-custodial staking. Tokens stay liquid; rewards vest after 90 continuous days.”**
- Before wallet connection, disclose reward vesting, forfeiture, claim fee, manual payout, and expected payout SLA in one readable terms card.
- Rename “Claim rewards” to “Request payout.” Show `requested → approved → sent → confirmed` status and the transaction link.
- Never use “claimed” or “paid” until the transfer is confirmed on-chain.

### CH-02 — Referral rewards and public metrics can be gamed with ghost stakes

**Severity: P0 — economic integrity**

`active_referrals()` counts `recorded_staked > 0`, not the effective stake capped by the current on-chain balance. A user can rotate the same tokens through referred wallets, call stake once in each wallet, transfer the tokens onward, and leave every wallet counted as an active referral. Fifteen ghost wallets reach the default +30% referral cap.

The leaderboard and protocol-wide `total_staked` metric also use `recorded_staked`, so wallets can remain highly ranked after moving their tokens out.

**Evidence**

- `db.py:308`: active referral query only checks `recorded_staked > 0`.
- `app.py:530`: leaderboard orders by `recorded_staked`.
- `app.py:657`: public stats sum `recorded_staked`.

**Required change**

- Define one canonical `effective_staked = min(recorded_staked, verified_balance)` value and use it for referrals, ranks, stats, eligibility, and reward accrual.
- Add a scheduled finalized-balance refresh for all active wallets and an expiry rule for stale balance snapshots.
- Require a meaningful minimum effective stake and minimum active duration before a referral contributes.
- Add an adversarial “rotate one balance through many wallets” test.

### CH-03 — Reward accrual is unsafe under the documented multi-worker scale model

**Severity: P0 before horizontal scaling**

`_accrue()` performs a read, calculates elapsed reward, then updates `accrued = accrued + reward` and `last_accrual_ts` without a row lock or compare-and-swap on the old timestamp. Concurrent requests in multiple workers can calculate from the same old timestamp and credit the same interval more than once.

This directly conflicts with the README's recommendation to run multiple workers for roughly 100k users.

**Evidence**

- `app.py:141`: non-atomic accrual read/calculate/update sequence.
- No concurrency test exercises accrual across workers or live Postgres.

**Required change**

- Make accrual a single transactional state transition.
- On Postgres, lock the staker row with `SELECT ... FOR UPDATE`; on SQLite, use `BEGIN IMMEDIATE`, or implement a CAS using the prior `last_accrual_ts` and retry.
- Add concurrent profile/stake/claim tests against real Postgres and SQLite with at least 50 simultaneous requests.

### CH-04 — Claims fail open when Solana RPC is unavailable

**Severity: P1 — money integrity**

The claim handler requests a forced live balance refresh, but `_refresh_balance(..., force=True)` catches every RPC error and returns the cached balance. The claim then proceeds using stale data. The code comment says a user cannot over-accrue after selling, but the implementation does not guarantee that during an RPC incident.

**Evidence**

- `app.py:113-121`: RPC exceptions always fall back to cache.
- `app.py:405-408`: claim relies on that forced refresh.

**Required change**

- For claim, payout-destination changes, and other money-finalizing actions, fail closed with `503` when a finalized balance cannot be fetched.
- Expose last verified balance time in the profile and observability metrics.
- Add a regression test proving an RPC failure cannot create a claim.

### CH-05 — Payout destination is mutable, bearer-token gated, and not snapshotted per claim

**Severity: P1 — account takeover and operator error**

The one-hour session token is stored in `localStorage`. That token alone can change the payout wallet; no fresh wallet signature is required. The claim row does not store its destination. `pay.py` looks up the user's current payout wallet at payment time, so a destination can change after the claim is created.

The manual settlement endpoint also accepts an arbitrary transaction signature without verifying destination, mint, or amount, and the schema does not prevent one transaction signature from being reused across claims.

**Evidence**

- `webapp/app.js`: `clw_token` stored in `localStorage`.
- `app.py:363`: payout address change needs only the session token.
- `db.py:354`: claim stores wallet and amount, not payout destination or fee breakdown.
- `pay.py:21`: payment destination is resolved from mutable current staker state.
- `db.py:388`: mark-paid does not verify or uniquely constrain the transaction.

**Required change**

- Require a fresh, domain-separated wallet signature for payout-destination creation or change.
- Snapshot immutable `destination`, `gross`, `fee`, `net`, and economic-rule version into every claim.
- Verify the treasury transfer on-chain before marking paid; make `tx_sig` unique.
- Move Mini App authentication to an opaque, revocable, HttpOnly session where platform constraints allow it. At minimum, add a strict CSP and remove unnecessary remote script execution.

### CH-06 — The security perimeter is weaker than the self-audit claims

**Severity: P1 — application security**

- The request-size middleware trusts `Content-Length`. A chunked request without that header bypasses the 16 KB check; the supplied Caddyfile has no body-size limit.
- There is no Content Security Policy while bearer tokens live in `localStorage` and the page executes remote Telegram code, dynamically imports Solana packages from `esm.sh`, and can inject the Jupiter plugin.
- Dependency ranges are not a lockfile. The clean audit environment resolved `starlette 0.49.3`, and `pip-audit` reported five known vulnerabilities.
- Production treats a missing Telegram token, public RPC, Redis, and admin payout token as warnings or optional even when those features are operationally required.

**Required change**

- Enforce streaming body limits in the ASGI layer and at Caddy.
- Add a strict nonce/hash-based CSP; bundle and pin runtime dependencies; remove dynamic CDN imports from money-moving paths.
- Commit a hash-locked dependency set, SBOM, and automated dependency/SAST scans.
- Make production configuration validation feature-aware and fail closed.

## UX and visual critique

### First impression

The onboarding screen is the best surface in the app. It is immediately branded, calm, and legible, with one obvious primary action. The glove is memorable and the tone is more premium than the average token Mini App.

The first dashboard screen loses that focus. A giant `0%` APR and three zero-value cards dominate before the user has connected a wallet. This turns the product's hero moment into an empty spreadsheet. “Connect to calculate your APR” would be more useful than presenting zeros as facts.

### Navigation and hierarchy

- Five bottom tabs are understandable, but “Trade” and “Boost” sit beside the primary staking job with equal weight. The product needs a clearer core loop: **Connect → understand terms → stake → track unlock → request payout**.
- Stake, unstake, and claim appear enabled while logged out. Tapping them opens the wallet sheet, but that is an indirect affordance. Logged-out states should use one primary connect CTA and show the other actions as unavailable with a reason.
- “Board” is less clear than “Leaders.”
- The trade screen looks clean, but it sends users into three overlapping purchase/swap paths. Pick one recommended route and move alternatives behind “More options.”
- Burn-to-boost is visually persuasive despite being irreversible and economically complex. It needs a permanent-risk explanation and an estimated payback calculation before any burn action.
- “Recent activity” is local device history, not server truth. Labeling it as account activity is misleading and it disappears across devices.

### Visual system

What works: palette, type pairing, card radii, spacing rhythm, restrained glass, motion reduction, and consistent illustration treatment.

What holds it below 9:

- Every card uses nearly the same treatment, so hierarchy comes mostly from size rather than structure.
- The enormous APR number over-emphasizes a modeled rate while claim status, unlock date, and payout state are secondary.
- Decorative sparkles, glow, three font families, and scripted count-up motion add atmosphere but also cognitive and performance cost.
- Focus treatment appears as a browser-default gold rectangle rather than a designed focus system.

## Performance and reliability

- `glove.png` is **811,593 bytes** and **664 × 1174**, yet is shown as small as 38 px. The first-party page payload is already about 1.0 MB before Google Fonts and Telegram resources.
- The app loads three font families and many weights. Google Fonts and the synchronous Telegram script are render-blocking dependencies.
- The image tags omit intrinsic width/height.
- The `/whitepaper` route returns HTTP 500 because `webapp/whitepaper.html` is absent.
- Python tests fail on the machine's Python 3.9 after a documented `pip install -r requirements.txt`; Pydantic cannot evaluate `str | None` without `eval-type-backport`. The project does not declare Python 3.10+.
- `notifier.py` says rewards are “ready to claim” without checking the 90-day unlock, payout setup, or claim fee.
- The deep health check does not validate RPC reachability, payout configuration, claim backlog age, or reconciliation freshness.

### Evidence not collected

- No real iOS/Android device or installed Phantom/Solflare/Backpack flow was exercised.

The app cannot honestly receive a 9/10 until those gaps are closed with evidence.

## Analytical plan to reach 9/10

### Phase 0 — Correct the promise and stop score inflation (1–2 days)

1. Remove the 9.2/10 claim from customer-facing or investor-facing material.
2. Rewrite onboarding around non-custody **and** reward vesting.
3. Publish claim fee, forfeiture rule, payout method, payout SLA, and treasury responsibility before connection.
4. Change all “claim succeeded” language to “payout requested” until an on-chain transfer is confirmed.

**Gate:** five unprompted users can explain when rewards unlock, what unstaking does, what claiming costs, and when tokens arrive.

### Phase 1 — Close money-integrity and takeover paths (5–8 engineering days)

1. Make accrual transactional and concurrency-safe.
2. Fix referral eligibility, leaderboard, and stats to use fresh effective stake.
3. Make claim balance verification fail closed.
4. Require a fresh wallet signature for payout-address changes.
5. Snapshot immutable claim economics and destination.
6. Verify and uniquely bind treasury transfers before marking claims paid.
7. Make burn credit + accrual + ledger recording one atomic transaction.

**Gate:** no open P0/P1 money findings; concurrency, RPC-outage, crash-between-commits, ghost-referral, replay, and payout-redirection tests pass against SQLite and live Postgres.

### Phase 2 — Rebuild the primary user journey and accessibility layer (5–7 design/engineering days)

1. Make the logged-out dashboard a purposeful preview, not a field of zeros.
2. Make the unlock date, vested/at-risk rewards, claim fee, payout state, and next action the main dashboard hierarchy.
3. Reduce trade choices to one recommended action plus secondary options.
4. Add irreversible-burn education and outcome simulation.
5. Implement accessible dialog, labels, tab state, focus styling, live regions, keyboard behavior, 44 px targets, zoom, and AA contrast tokens.
6. Replace local-only “Recent activity” with server-backed claim/stake/burn history or label it honestly.

**Gate:** axe reports no serious/critical issues; manual keyboard, VoiceOver, and TalkBack scripts pass; all core screens remain usable at 200% zoom.

### Phase 3 — Performance, supply chain, and failure handling (4–6 engineering days)

1. Crop and encode the glove asset as AVIF/WebP with a small PNG fallback; target under 50 KB for the app icon asset.
2. Reduce to two font families and self-host a minimal subset.
3. Defer noncritical scripts and bundle pinned Solana/Jupiter code used by financial actions.
4. Add CSP, edge and ASGI body limits, locked dependencies with hashes, SBOM, and CI security scans.
5. Repair or remove `/whitepaper`; make broken static routes impossible in CI.
6. Declare and enforce the supported Python version.
7. Correct notifications so “claimable” matches the API's real gates.

**Gate:** mobile p75 LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 on the production URL; no known high/critical dependency vulnerabilities; forced network failures produce truthful recovery states.

### Phase 4 — Operational proof (5–10 engineering/QA days)

1. Add metrics for accrual retries, stale balances, RPC errors, claim backlog age, payout latency, reconciliation drift, Redis health, and DB contention.
2. Define SLOs and alerts; publish the payout SLA.
3. Run a documented production-shaped load test using Postgres and Redis with at least 2× expected peak headroom.
4. Perform an off-box backup restore drill and prove recovery time/objectives.
5. Exercise Phantom, Solflare, and Backpack on real iOS and Android devices, including app switching, cold relaunch, cancellation, expired sessions, and poor networks.
6. Run an independent financial-logic/security review and remediate all high findings.

**Gate:** no open P0/P1 findings, reconciliation is clean after load/chaos runs, payouts are traceable end to end, and the real-device matrix is signed off.

## What a real 9/10 looks like

A 9/10 release is not the current UI with more animation. It has:

- precise economics before wallet connection;
- no path to create rewards or boosts from concurrency or stale/ghost balances;
- payout destinations that cannot be redirected by a stolen bearer token;
- immutable and on-chain-verifiable claim records;
- a dashboard centered on unlock and payout truth;
- WCAG 2.1 AA behavior, not just attractive colors;
- sub-2.5-second production mobile loading;
- real-device wallet evidence;
- production-shaped load, restore, reconciliation, and security evidence;
- no self-awarded audit score.

**Estimated path:** roughly **4–6 focused weeks** for one senior full-stack engineer with design/QA support, followed by independent review. The schedule shortens if the payout model remains manual, but the trust and verification requirements do not.
